<architecture>
Two processes. Do not collapse them.
1. In-process agent: an OSGi bundle injected into the target Eclipse JVM. It runs inside the UI runtime so it can reach the SWT Display, workbench, and jobs. It exposes a small loopback-only, token-authenticated RPC endpoint (HTTP+JSON or WebSocket; pick one and justify it in a short ARCHITECTURE.md).
2. MCP server: a standalone process speaking MCP over stdio. It launches or attaches to the target, loads the agent, and translates MCP tool calls to agent RPC.

Attach modes (both required):                                                                                                                                    - launch: start the install given its path, with the agent bundle rhe install (e.g. `-Dosgi.bundles` or `-Dosgi.framework.extensions`via launcher args, `-vmargs`, or a separate configuration area). Never write into the user's install directory.                                                  - attach: connect to an already running instance via JVM Attach APIad a Java agent, and have it install and start the OSGi bundle. Fall back to a clear error with diagnostics if attach is disabled.                                                                                                    
Use SWTBot where it helps (widget lookup, matchers, waits). Fall back to direct SWT `Display.syncExec` / widget-tree traversal where SWTBot is limited. Resolve  SWTBot and SWT dependencies against the target's own bundles when pw. All UI access MUST go through the correct thread: the UI threadfor widget access, and never block the UI thread while waiting.                                                                                                  </architecture>

<interview-me>
- Outcome: One shippable MCP server plus a single-plugin OSGi agent. An AI can use any Eclipse RCP product the way a human does. That is about 70 tools plus basic native-dialog handling. It covers editing AUTOSAR configs, building from Build Control, running and debugging JUnit Plug-in Tests, reading results, fixing, rerunning, and feature testing with feedback.
- User: You, with Claude Code on ISOLAR-AB first (bundled JDK 21, Equinox 3.23, SWT 3.130). It must also work on RCP installs it has never seen.
- Why now: You want the AI to run edit, build, test, fix loops by itself. ISOLAR's own MCP is model-level and cannot reach the GUI.
- Success:
  a. The AI edits a config and runs the build from Build Control.
  b. The AI starts a JUnit Plug-in Test through a Debug configuration or run_script, which streams output and returns the exit code.
  c. The AI reads the parent's JUnit, Console and Problems views.
  d. The AI observes and acts in the child instance, which it attaches to explicitly.
  e. The AI edits the testcase and reruns.
  f. The AI works through a Browse button's native file dialog end to end.
  g. In feature-tester mode, the AI records findings in a session journal, and the opt-in call trace feeds the improvement feedback.
- Constraints:
  - Loopback only, with a per-session token.
  - No eval tool.
  - Nothing is written into the install directory.
  - All widget access goes through the UI thread.
  - Waits always time out.
  - Errors are structured.
  - Modal dialogs never block observation.
- Assumptions (changed):
  a. Agent: one OSGi plugin. You develop it in your Eclipse against the .target file, which is the compile classpath only. It requires the target's own bundles and
     bundles nothing from them.
  b. Server: a separate fat jar that embeds the agent jar. It extracts the agent to a temp or config area on launch.
  c. SWTBot: I use it only if the target contains it. Otherwise I uc and widget traversal. I would use direct SWT only, so the agenthas no runtime dependency on it.
  d. Java release: pinned from the oldest runtime in the target, anget file.
  e. Build: a .target file is awkward for the command line, so the dev build is a PDE project in your Eclipse. The ship build is build.cmd using the bundled JDK and
     jar, with no Maven. If you would rather have Tycho, say so.
  f. Native dialogs: Windows only, handled from the server process.
- Out of scope:
  - Model-level AUTOSAR APIs.
  - Remote access.
  - Eval.
  - Non-SWT UIs.
  - Desktop automation beyond native dialogs of the Eclipse process.
  - Publishing and git init.
